## Objetivo para esta sesión
Construir un visor de fotos web de ejecución local que cargue imágenes desde un directorio del sistema, las muestre en pantalla completa en orden alfabético en ciclo continuo, y utilice morphing como transición entre ellas. Máxima fluidez y velocidad como prioridad técnica.

---

## Stack Técnico Elegido

- **Servidor local**: Python 3.x (`uvicorn` + `fastapi` para endpoint REST simple y servir estáticos con alto rendimiento).
- **Frontend**: HTML + CSS + JavaScript vanilla (sin frameworks, para máximo rendimiento).
- **Transición (morphing)**: Web Animations API + doble `<img>` con `@keyframes` (blur + scale + opacity). Evaluar WebGL/canvas como segunda opción si el efecto CSS no es suficiente.
- **Carga de imágenes**: Precarga (`Image()` JS) de N+1 y N+2 para garantizar cero latencia.
- **Testing backend**: `pytest` para unit tests del servidor Python.
- **Testing frontend**: Tests manuales con checklist de verificación en navegador.
- **Documentación**: Docstrings en Python, JSDoc en JS, y `docs/` para documentación de usuario y técnica.

## Bugfixes (surgidos durante la sesión)

### BF-01: StaticFiles interceptaba rutas /api/foto/
- **Síntoma**: Al presionar "Iniciar", las imágenes devolvían 404 desde el `<img>` del frontend; el slideshow no arrancaba.
- **Causa raíz**: `StaticFiles` montado en `/` tenía mayor prioridad que las rutas FastAPI, interceptando `/api/foto/...` antes de que pudiera manejarse.
- **Causa secundaria**: `display: flex` en `.config-screen` anulaba el atributo `[hidden]` del UA stylesheet, impidiendo ocultar la pantalla de config vía JS.
- **Fix**:
  - `StaticFiles` movido de `/` a `/static`.
  - `GET /` sirve `index.html` explícitamente.
  - Añadido `[hidden] { display: none !important }` en `style.css`.
  - `_loadImage()` corregido para manejar imágenes en caché (`imgEl.complete`).
  - `tests/conftest.py` añadido para resolver imports dentro del venv.
- [x] Resuelto y verificado en navegador.

### BF-02: Dropdown de favoritos incompleto y sin scroll
- **Síntoma**: El menú desplegable corta la lista de directorios y no permite desplazarse si hay muchos elementos. Los favoritos pueden quedar truncados por el límite de 8 de la lista de recientes.
- **Estrategia**:
  - **CSS**: Establecer `max-height: 250px` y `overflow-y: auto` en `.recent-dirs`. Estilizar el scrollbar.
  - **JS**: Diferenciar visulamente favoritos (con una estrella ★) de recientes.
  - **JS**: Modificar `renderRecentDirs` para que concatene la lista completa de favoritos + la lista de recientes (sin duplicados), mostrando siempre todos los favoritos arriba.
- [x] Implementar cambios en `style.css` y `app.js`.
- [x] Verificar scroll y persistencia de la lista extendida.

### BF-03: Dropdown no hace scroll y se sale de pantalla
- **Síntoma**: El dropdown muestra todos los favoritos pero se extiende fuera del área visible sin scroll.
- **Causa raíz**: `.recent-dirs` está en flujo normal del DOM. Cuando crece, empuja el contenido y desborda el viewport. El `overflow-y: auto` en la lista no actúa porque el elemento crece libremente.
- **Fix**:
  - Hacer `.recent-dirs` posicionado absolutamente (`position: absolute`, `z-index` alto) para que flote sobre el resto del contenido.
  - El contenedor padre `.dir-input-wrapper + ul` debe tener un ancestro con `position: relative` para contener el posicionamiento.
  - El `max-height` y `overflow-y: auto` en `.recent-dirs` funcionarán correctamente una vez que esté fuera del flujo normal.
- [x] Aplicar `position: absolute` y ajustar `top`/`width` para alinearlo correctamente bajo el input.
- [x] Verificar scroll con lista larga en navegador.

## Mejoras (surgidas durante la sesión)

- **Implementación**:

  - `selectedPreload` pasado desde la UI al constructor.
- [x] Implementado y verificado en navegador.

### M-02: Foto completa sin recorte
- **Motivación**: Las imágenes se expandían a los lados pero se recortaban arriba y abajo.
- **Implementación**: `object-fit` cambiado de `cover` a `contain` en `.slide-layer`.
- [x] Implementado.

### M-03: Morphing más rápido
- **Motivación**: La transición de 1.2s se sentía lenta.
- **Implementación**: Duración de `morphOut` y `morphIn` reducida de `1.2s` a `0.6s` en `style.css`.
- [x] Implementado.

### M-04: Historial de rutas recientes
- **Motivación**: Tener que escribir la ruta completa manualmente cada vez es tedioso.
- **Implementación**:
  - `localStorage` guarda hasta 8 rutas, ordenadas por uso reciente.
  - Botón chevron (▾) junto al input abre un dropdown con el historial.
  - Click en una ruta la copia al input; botón "✕ borrar" elimina entradas individuales.
  - Al cargar la app, el input se pre-rellena con la última ruta usada.
- [x] Implementado.

### M-05: Favoritos en la UI

- **Implementación**:

  - Textarea para ingresar rutas (separadas por salto de línea).
  - Al dar a guardar, las guarda en `localStorage` (como favoritos) y las inyecta también permanentemente a la lista de recientes (verificando limpieza de duplicados).
- [x] Implementado.

### M-06: Precarga desactivada por defecto

- **Implementación**: Estado inicial puesto en `false` en `app.js` y clases en UI ajustadas.

## Introspección de la Sesión

> *Reflexión del agente, luego enriquecida por el PM (D. Schön, reflection-on-action).*

**TL;DR**: ~1,500+ líneas de código en 14 archivos, 13 tests, 3 bugs resueltos (BF-01..03), 7 mejoras emergentes (M-01..07), reglas de agente evolucionaron de 6 a 10. El reto real no fue el morphing (CSS lo resolvió trivialmente), sino la integración entre FastAPI, el DOM y el browser cache. El sistema documental no fue diseñado — emergió de la fricción del proceso.

### Cadena de decisiones

```
Objetivo vago ──► Stack (FastAPI+vanilla) ──► Backend ──► Frontend ──► Morphing (CSS keyframes)
     │                                            │           │              │
     ▼                                            ▼           ▼              ▼
  Bugs emergentes ► BF-01 StaticFiles ► BF-02 dropdown ► BF-03 overflow
     │
     ▼
  Mejoras emergentes ► M-01..M-05 (preload, contain, historial, favoritos)
     │
     ▼
  Meta-mejoras ► M-06 (morphing 0.6s) ► M-07 (regla 2 pasos)
```

#### Micro-decisiones clave

| # | Micro-decisión | Contexto | Impacto |
|---|---------------|----------|---------|
| 1 | `object-fit: contain` en vez de `cover` | Las fotos se recortaban | 1 línea CSS, cambió toda la experiencia (M-02) |
| 2 | Transición 1.2s → 0.6s | Se sentía "pesada" | Ajuste perceptual, fluidez percibida ×2 (M-03) |
| 3 | `StaticFiles` de `/` a `/static` | 404 en todas las imágenes | Primer bug crítico; orden de montaje en FastAPI (BF-01) |
| 4 | `[hidden] { display: none !important }` | `display: flex` anulaba `hidden` | Bug sutil: UA stylesheet vs reglas explícitas |
| 5 | `imgEl.complete` check | Caché no dispara `onload` | Sin esto, la primera foto nunca aparecía si estaba cacheada |
| 6 | `position: absolute` en dropdown | Empujaba todo el layout | 3 intentos; el problema era flujo del DOM, no `overflow` (BF-03) |
| 7 | Precarga desactivada por defecto | Cientos de fotos ralentizaban arranque | Inversión de supuesto: "precargar siempre es mejor" → falso (M-01) |
| 8 | Proceso de 2 pasos | El agente iba directo al código | Meta-decisión que cambió el flujo de trabajo completo (M-07) |

### Sorpresas

**1. Integración > diseño.** El objetivo decía "máxima fluidez y velocidad". Asumimos que el reto estaría en el morphing (¿WebGL? ¿Canvas?). CSS keyframes con `will-change` y `cubic-bezier` lo resolvieron en 60fps. Los problemas reales fueron de integración: `StaticFiles` interceptando rutas API (BF-01), `display:flex` anulando `[hidden]`, `onload` no disparando en cache. El cuello de botella fue cómo el servidor, el CSS y el navegador interactúan en sus propios "micro-mundos".

**2. Precarga contraproducente.** La precarga N+1/N+2 se diseñó como feature premium. Con carpetas grandes, bloqueaba la UI. El heurístico "más anticipación = más velocidad" falla cuando el costo de anticipar supera la latencia puntual. Solución: opt-in, no forzar.

**3. El sistema documental emergió de la fricción.** No hubo diseño previo de `log.md`, `planning/`, `technical_stack.md`, reglas en `README.md`. Cada uno nació de un problema concreto: `log.md` para no perder rastro; `planning/` cuando el agente implementaba sin alinear; la regla de 2 pasos cuando el PM necesitó revisión; la regla 8 por la fricción de registrar doc-changes en sesión.

### Aprendizajes

1. **Integración > implementación en costo real.** Elegir FastAPI, CSS keyframes, vanilla JS fue rápido. Pero *cómo* interactúan (montaje de `StaticFiles`, `display:flex` vs `[hidden]`, `onload` en cache) consumió más tiempo que todo el diseño combinado. *Implicancia*: la palabra "integración" debería tener más peso presupuestal que "implementación".

2. **Protocolos humano-IA se diseñan en caliente, no en frío.** La regla de 2 pasos (M-07) no podría haberse diseñado antes de experimentar la fricción. Los protocolos emergen de la experiencia vivida. *Implicancia*: las reglas iniciales del `README.md` deben ser pocas; las valiosas surgirán de los bug-fixes del proceso.

3. **Satisficing es estrategia, no limitación.** CSS vs WebGL, `localStorage` vs SQLite, vanilla vs React — la primera solución suficientemente buena no cerró puertas y permitió velocidad. *Implicancia*: para proyectos de prototipo-a-producto, el satisficing (Simon) es estrategia competitiva.

### Reflexiones del PM (Schön)

> *Añadidas post-propuesta del agente, como reflection-on-action.*

1. **Optimización de tokens**: El PM ajustó manualmente el modelo del agente varias veces durante la sesión para reducir consumo de tokens. Esta intervención invisible afectó la calidad y extensión de las respuestas. El agente no lo detectó — un punto ciego del proceso.
2. **Granularidad log ↔ sesión** (deuda abierta): La frontera entre qué va en `log.md` vs `session-*.md` no está resuelta. Hay redundancia y gaps. Se registra como deuda a resolver en una sesión futura.
3. **Nomenclatura BF-XX/M-XX**: La decisión del agente de estandarizar un lenguaje para bugs y mejoras fue una sorpresa positiva. Formalizada como regla 10.
4. **Verbosidad vs compresión**: La introspección v1 era correcta pero excesivamente verbosa; la v2 demasiado críptica. Los documentos deben apuntar al **mínimo viable con desarrollo suficiente** para extrapolación sin dificultad.
